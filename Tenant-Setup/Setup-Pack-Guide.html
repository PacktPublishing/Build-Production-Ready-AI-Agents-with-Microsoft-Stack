Claims 365 setup pack

Everything the Claims 365 exercises need in Dataverse, packaged so you can import it into your own tenant through the browser. One solution file, six spreadsheets, and about an hour — twenty minutes of clicking and the rest waiting for imports to run. No scripts, no command line, nothing to install.

✅ No compiled code, no scripts — and six flows that do run

Being precise, because the difference matters to whoever approves this: there is no compiled code, no script and no macro anywhere in this pack. There are six Power Automate flows, which are executable logic — they run as you, they are itemised below, and you can read every one before you turn it on.

The pack contains exactly four kinds of file: a .zip Dataverse solution (which is XML inside — open it and read it), .csv spreadsheets (plain text), a .json schema, and .txt/.html documents. There is no .exe, no .dll, no .ps1, no macro-enabled Office file and no .js anywhere in it. CSV was chosen over XLSX deliberately: a .csv is incapable of carrying a macro, and you can read every row in Notepad before you import it.

CHECKSUMS.txt lists a SHA-256 for every file. On Windows, Get-FileHash <file> confirms one. Nothing in this pack asks you for a password, a key or a token.

What is actually inside the solution file, for anyone who has to sign it off

If a security reviewer has to approve this, hand them this section. Unzip Claims365SetupPack_1_0_0_0.zip and you will find exactly nine files and nothing else:

solution.xmlThe component list. 5 KB
customizations.xmlEvery table, column and the security role, as XML. 934 KB, and readable
[Content_Types].xmlThe archive's own manifest. 258 bytes
Workflows/ (6 files)One JSON definition per flow, 2–10 KB each, also readable
⚠️ Four things a reviewer will find, and what each one is

1. The words PluginAssembly, PluginType and SdkMessageProcessingStep appear in customizations.xml. They are not assemblies. They are the names of read privileges on the security role (prvReadPluginAssembly and friends) — the defaults Dataverse gives any new custom role. A solution carrying a real plug-in ships the compiled DLL as a base64 <Content> element. Search this file for <Content> or base64: both return zero. There is also no WebResource (which is how JavaScript would arrive) and <CustomControls /> is an empty element.

2. Every flow references schema.management.azure.com. That is the $schema declaration every Power Automate flow definition carries. It is a namespace identifier, not a call, and nothing fetches it.

3. One GUID is hardcoded, in Claims 365 Customer Claim Lookup: a directory (tenant) id belonging to the course's demo Entra External ID tenant. It is the value the flow checks a customer's sign-in token was issued by. A tenant id is not a secret — every tenant's is public and discoverable — and it grants nothing. But you must replace it with your own external tenant's id if you reproduce the customer sign-in path, or your gate validates against a directory you do not control and refuses everyone. Chapter 1, Creating the external customer directory, says where. Not doing Chapter 3's customer sign-in? Delete that flow.

4. One flow makes one genuine outbound call. Claims 365 Customer Claim Lookup calls https://graph.microsoft.com/oidc/userinfo to validate a signed-in customer's token — it is the identity check that makes Chapter 3's customer sign-in gate real, and it is deliberate. The other five flows talk only to Dataverse. If you are not reproducing the customer sign-in path, you can delete that flow after import and nothing else changes.

What the security role grants

Claims 365 Attendee is a custom role with 25 privileges. Nothing in it touches a standard Dataverse table beyond the defaults a new role is created with:

PrivilegeOn what
Read, organisation-wideThe six data tables: Policy, Claim, Approved Repairer, Claims Guidance, Claimant, Book Claim
Read + Create organisation-wide, Write / Append on own recordsThe two referral tables Chapter 5's Fraud Desk writes to

There is no Delete privilege at any depth, on anything. The role grants nothing outside the ten cp_ tables and those Dataverse defaults, and assigning it to yourself cannot widen anyone else's access.

2 Before you import

⚠️ Import into an environment you created for this, not your default one

Do not have one yet? Chapter 1, Creating the Dataverse environment, creates it in about ten minutes.

Two reasons, and the second is the one people regret. First, some tenants switch on Block unmanaged customizations, which refuses this import outright and also stops Copilot Studio publishing an agent — so it breaks the exercises, not just the pack. A fresh environment you make yourself will not have it. Second, deleting the environment is the only teardown that actually removes everything (see section 9).

If you already use the cp prefix for your own work, a separate environment stops the two colliding.

🚨 If you are on the Power Apps Developer Plan, read this now

Microsoft does not include Get data from Excel or Export data in the Power Apps Developer Plan. The per-table import in step 6a will simply not be there, and it looks exactly like the pack being broken.

Use step 6b instead — the Data import wizard in the Power Platform admin center, which is available to you and takes all six files in one pass. The same applies in GCC, GCC High and DoD, where the per-table import is also unavailable.

3 Create the Dataverse connection first

Two minutes now saves the most common failure in the whole process.

In make.powerapps.com, check the environment picker at the top right is on the environment you are setting up, then go to Data → Connections → + New connection, search for Microsoft Dataverse, and select Create. Sign in when prompted.

⚠️ Do this before the import, and do the whole setup as one identity

The import wizard will let you create a connection halfway through, but it opens a second browser window and people lose their place. More importantly: whoever runs the import owns every component in it — the flows and the connection reference included. If a colleague or an admin imports "to help", you will not be able to turn the flows on. Connection-reference ownership cannot be reassigned from the modern Solutions area, so this is much cheaper to get right than to fix.

5 Publish all customizations

🚨 Do not skip this, and do it before importing any data

An unmanaged solution imports in a draft state. Until you publish, the tables exist but are not fully active — and the data import in the next section will either not see them or will map their columns wrongly. This is the single most common reason a pack "imports fine" and then does nothing.

Open the imported solution and select Publish all customizations on the command bar. Wait for it to finish before continuing.

6 Load the data

432 rows across six tables. Order does not matter — none of these tables uses a lookup column, deliberately, so there are no parent rows to load first.

6a. The normal route: one table at a time

  1. Tables in the left navigation, then open the table — start with Policy.
  2. Import → Import data from Excel, then Upload and choose the matching CSV. The file names match the table names exactly, so Policy.csv goes on the Policy table.
  3. Wait for Mapping status to read Mapping was successful. If anything is flagged, open Map status and resolve it before continuing.
  4. Select Import. When it finishes, check the number of rows created against the count in the table below.
  5. Repeat for the other five.

6b. The fallback route: all six at once

Use this if step 6a's command is missing (Developer Plan, or a government cloud), or if you would rather do it in one pass. Power Platform admin center → Environments → your environment → Settings → Data management → Data import wizard, and upload All-six-tables.zip. The wizard maps each file to its table, and each column to its column, automatically: the file names match the table display names and the headers match the column display names exactly. Check the mapping screen before you commit anyway — it takes ten seconds and it is the only place a mismatch shows up before the rows land.

🚨 If an import goes wrong, do not simply run it again

These tables carry no alternate key, so the importer has nothing to match an existing row on. It therefore adds every row in the file as a new record, every time. A second run leaves you with 6 policies and 372 claimants, and the agent then retrieves contradictory data.

The recovery is to delete the rows first and re-import: open the table's Data tab and delete them, or use Power Platform admin center → Settings → Data management → Bulk deletion for the larger two.

⬜ Two of the six flows, and four of the ten tables, are only for the optional parts

You want four flows. Claim Lookup and Policy Lookup are the verified pair behind Chapter 2's lookup tools; Repairer Lookup and Guidance Lookup serve public information and check nobody. Customer Claim Lookup belongs to Chapter 3's optional customer sign-in, and Entitlement Lookup is superseded — the verified Claim and Policy pair replaced it, and nothing in the book calls it. Do not build anything on it, and delete it if you like.

Four tables ship empty by design and there is nothing missing: Submission fills up when the claim form in the Website folder assesses a claim (Chapter 4), Fraud Referral and Referral Claim when Chapter 5's Fraud Desk writes a referral, and Entitlement is the table you seed yourself with your own customer's object id — Chapter 1, Creating the external customer directory, says how.

9 Removing it again

🚨 Deleting the solution does not uninstall anything

In Microsoft's own words: deleting an unmanaged solution "deletes the solution container but doesn't delete any of the unmanaged components within. Any data associated also remains." You will see a confirmation, believe your tenant is clean, and every table, flow, role and row will still be there — now orphaned into the default solution.

The clean teardown is to delete the environment you imported into (Chapter 1 created it). That removes everything at once. Note the default environment cannot be deleted, and a deleted environment's URL cannot be reused for about 24 hours.

If you must keep the environment, delete manually and in this order: the six cloud flows, then the connection reference, then each table (which destroys its rows irrecoverably), then the security role, then the solution container.

⬜ About the postcodes, before anyone asks

The 186 claimant postcodes use real UK outward codes — M14, M20, SE15, EH8, LS7 and a few others — because the fraud scenario depends on a cluster of claimants living plausibly near one another, and invented outward codes would look obviously synthetic. The inward halves are generated and most are not deliverable addresses.

This is not personal data: a postcode identifies an area of roughly fifteen households, not a person, and every name, email, phone number and bank detail attached to them is invented. If your reviewer would rather the outward codes were randomised, they carry no teaching weight — only the clustering matters: five claimants share the postcode M20 4WX, and six claims in Book Claim.csv record it as the incident location. Replace them freely, as long as those rows still match each other.

Claims 365 and Contoso Insurance are training fiction. Every policyholder, claim, claimant, bank account, phone number and email address in this pack is invented: the phone numbers use Ofcom's reserved drama range, the sort codes use an unissued range, and the email domains use the reserved .example top-level domain, which cannot receive mail. Nothing here is anyone's real data.
